### Companies page (done)

- A "company" is a `departments` row with `is_company=1` — same `Department` model, no new model needed. New `CompanyTime` model wraps the already-live `companies_times` table (`dep_id, start_time, end_time` — a per-company gate check-time window, parallel to but distinct from `check_times`; optional, not every company has a row).
- **Real reuse of the Employees console, not a duplicate**: `/companies/{company}` renders the exact same `employees/Employees.vue` page (same composable, same components) with an extra `lockedCompany` prop, instead of legacy's hand-copied ~1000-line near-duplicate page. Employee create/update/delete/approve/cars/access-card/movements all go through the existing `/employees*` routes completely unchanged — only `EmployeeService::applyFilters()` gained a `company_only` branch.
- **Corrected a scoping gap while doing this**: legacy's real employee-list query (`applyEmployeeCompanyScope()`) filters by `departments.is_company` (0 for the regular grid, 1 for a company's roster) — gateNew's `EmployeeService::list()` didn't previously make this distinction at all (reachable only via a hand-crafted `dep_id` URL param, since the UI couldn't select a company before this page existed). Now enforced explicitly in both directions.
- `is_employee` (added to `Employee::$fillable`, previously entirely absent from it despite existing on the model/docblock) is a record-type marker set by the locked create form, **not** what scopes the list — that's `dep_id` + `departments.is_company`. Confirmed via live data before assuming: 1,271 real employees already have `dep_id` pointing at a company (top: "DCI", 280) while `is_employee` was `0` on all 14,679 rows.
- **Real bug found in `Department::$fillable`, fixed**: `is_company` was missing from it entirely — `Department::create(['is_company' => 1, ...])` was silently mass-assignment-dropping the flag, so a "company" created that way wasn't actually flagged as one (caught by the smoke test before it ever reached the browser).
- **Badge seeding**: reused `DepartmentService::create()`'s existing lightweight default-badge insert (extracted into `seedDefaultBadge()`) instead of porting legacy's second, much larger hardcoded front+back template. `DepartmentTreeService::getNestedTreeIncludingCompanies()` (used only by the Badge Designer's picker — every other tree consumer keeps excluding companies via the existing `getNestedTree()`) makes a company selectable there, so an admin can now visually design its badge instead of being stuck with the generic default.
- **Legacy bugs not replicated**: legacy's "edit company" flow actually POSTs to the create endpoint (so an edit inserts a duplicate row instead of updating) — this app has a real `PUT` update endpoint. Legacy also has no delete action wired for companies at all (dead, unused code exists) — this app adds one, matching Departments' global-scope-only, non-cascading delete.
- Company visibility is scoped via the `departments` resource's own scope (`companies` isn't independently scopable, same as `employees` isn't) — global sees all, hierarchy sees companies within the actor's subtree. This replaces legacy's cruder "only companies whose `parent_id` is literally my own `dep_id`" rule.
- **Deferred, unchanged**: the cross-company "بحث عام" global employee search bar (already flagged deferred with Employees, specifically tied to Companies — still deferred, now unblocked whenever wanted) and `CompaniesReporting.vue`/`CompaniesIssues.vue` (confirmed genuinely separate component trees/backend services/routes, not linked to or from the main Companies page).

### Time Settings page (done)

- Scope is CRUD-only on `check_times` (per-department, per-gender, per-rank-category check-in/check-out windows) — matches what the legacy `Settings.vue` page itself does. The _consumption_ side (late-arrival/early-exit calc reading these rows — `EmployeeService::guestInfo`, `ReportQueryService`, the `employee_specific_movements_notes_view` SQL view, and the two still-deferred Dashboard charts `issuesByDepartment`/`issuesTrend`) is a separate, already-twice-deferred effort — not touched here.
- `check_times.rank_id` is a foreign key to `ranks_categories.id` (the coarse category: Officers/Other Ranks/Civilians/Customs), **not** `ranks.id` — same naming trap as `ranks.rank_id` itself. Named the new model's relation `rankCategory()` to keep this unambiguous.
- Added real backend validation where legacy had none (`StoreCheckTimeRequest`/`UpdateCheckTimeRequest`): `rank_id` is required (legacy's frontend never required it, and the DB column is `NOT NULL` — submitting without one threw a raw SQL error in legacy), and both time fields must match `H:i` format (legacy used free-text inputs with no format enforcement at all — replaced with native `<input type="time">`).
- Added an application-level uniqueness check on `(dep_id, gender_id, rank_id)` via `Rule::unique('check_times')->where(...)` — legacy has no DB unique index and no app-level duplicate check; all downstream consumers pick whichever duplicate matches first if this were ever violated, so this is cheap insurance, not a legacy behavior change users would notice.
- Deliberately dropped legacy's "auto-select the first child department under the user's root department" default-selection quirk on page load — simplified to no default selection (empty state prompting the admin to pick a department). `settings` isn't a scopable resource (`config/access.php`), so any admin with `settings.read` can pick any department in the tree; there's no natural per-user default department for global-scope roles like Super Admin anyway.
- **Bug hit and fixed**: the edit dialog originally pre-filled `start_time`/`end_time` straight from the DB's raw `HH:MM:SS` values (Eloquent doesn't cast `TIME` columns to strip seconds). If a user edited only one of the two time fields, the untouched one still carried seconds and failed the new `date_format:H:i` validation on save — silently blocking the update (Inertia's error redirect looks identical to a success redirect at the HTTP-status level, so this took some digging to isolate). Fixed by slicing both fields to `HH:MM` when populating the edit form (`useSettingsPage.ts`'s `openEditDialog()`), matching what the table display and legacy's own `formatCheckTime()` (`substr($value, 0, 5)`) already did.
- **Bug hit and fixed (same class as the `defaultBase()`→`default_base` gotcha in Employees)**: the `CheckTime` model's `rankCategory()` relation serializes to JSON as snake_case `rank_category`, not `rankCategory` — Eloquent's `Str::snake()`-on-relation-keys default. The frontend type and the table's cell template both referenced `data.rankCategory`, which is always `undefined`, so the Rank Category column silently rendered blank for every row (caught after shipping, via a screenshot, not before). Fixed by renaming the TS field and template reference to `rank_category`. Worth checking the actual JSON shape (not just assuming the relation method name) whenever a new camelCase relation is added and consumed on the frontend.

### Users admin page (done)

- Cloned the legacy `Users.vue` **workflow** only, not its implementation: list/search/filter, create/edit via a slide-over panel (matching this app's established Employees/Departments pattern, not legacy's AG-Grid + client-side-filter-everything approach), single-role assignment, department + default-base assignment, delete.
- **Two deliberate behavior additions beyond legacy** (legacy has neither): (1) an admin can't lower their own role or delete their own account through this page, and (2) the last remaining Super Admin can't be demoted or deleted via this page. Enforced in `UserService::assertRoleChangeAllowed()`/`assertDeletable()`, called from `UserController` before the write — not in the FormRequests, since these checks need the target's current DB role and a table-wide count, which is a different kind of check than the FormRequests' static config-driven validation (matches this app's existing precedent of putting that class of check in `DataScopeResolver`/controllers, not FormRequest `withValidator()` hooks — no FormRequest in this app uses one).
- **Keycloak SSO "pending activation" workflow completed**: legacy's equivalent (and this app's own `KeycloakAuthService::provisionPendingUser()`, already built but previously unconsumed) creates a department-less stub user on first unrecognized Keycloak login. This page is the first UI that lets an admin set role + department to activate one (`activate_sso` checkbox in the edit panel, atomic with the rest of the save). Department-less users are deliberately visible to hierarchy-scoped (not just global-scope) admins via an `orWhereNull('dep_id')` clause in the list scope query — without it, only Super Admin could ever activate a pending account.
- **Role assignment lives only in this page's form** (a single role `<Select>`) — legacy has a second, less-guarded path to change a user's role via its separate Roles page's "linked users" widget. That page doesn't exist in gateNew yet; when it's built, don't reintroduce that duplicate path.
- Role options (both the create/edit picker and the list's role filter) are always `AccessCatalog::assignableRoleNamesForActor($actor)` — the same list, reused, not two hand-maintained lists that can drift.
- **Fixed a bug before it happened**: `users.default_base` is `int NOT NULL DEFAULT 0` live (confirmed via `DESCRIBE`, not assumed) — same NOT-NULL-column-assumed-nullable trap as `bases.name_ar` above. The FormRequests validate a null-coerced value (`''`/`0` → `null`, so `exists:bases,id` only ever checks a real id); `UserService::prepareFields()` coerces `null` back to `0` before saving.
- `keycloak_sub` also carries a live UNIQUE index — `UserService::update()` checks no other user already holds the target `keycloak_pending_sub` value before activating, so a conflict surfaces as a clean validation error instead of a raw DB integrity exception.
- Server-side validation added where legacy had essentially none: real `unique:users,username` (legacy relied on a raw DB exception), `min:8` password (legacy: 6), config-driven role assignability (`Rule::in(assignableRoleNamesForActor())`), conditional department requirement (`roleRequiresDepartment()`).
- Added a **confirm-password field** on the create panel (`password_confirmation`, Laravel's `confirmed` rule) — not present on legacy's create form. Edit's password field stays single-field/optional (blank = unchanged), unaffected.
- Verified via a rolled-back `DB::transaction()` in tinker, not by manipulating real accounts: the live DB currently has 4 Super Admins (2 real + 2 leftover Playwright test accounts from earlier sessions — worth cleaning up eventually), so the last-admin guard can't be triggered safely through the UI. Demoted all-but-one inside a transaction, exercised both guard methods directly, then rolled back — confirmed zero persisted change afterward.

### Gate Kiosk & Plate Movements page (done)

- Ported the actual reference workflow from `gate/backend/app/Services/Movements/MovementCheckService.php` + `gate/backend/app/Support/EmployeeGateAlerts.php` (a genuinely proven, offline-first implementation in the older Vue-SPA stack, not the Inertia one) — not designed from scratch. Two Inertia pages: `/gate` (kiosk) and `/gate/plate-search` (read-only movement history by plate).
- **Architecture**: `/gate` is a normal Inertia page whose Vue component then behaves as a self-contained mini-app for the whole shift — no `router.visit` afterward, all lookups/submits via plain `fetch()`/`csrfPost`. A service worker (`vite-plugin-pwa`, `generateSW` mode, `injectRegister: false` + manual `virtual:pwa-register` call in `app.ts` since there's no static `index.html` to auto-inject into) does a `NetworkFirst` cache of the `/gate*` shell and `CacheFirst` caches of `/uploads/*` photos — repeat loads (refresh, reboot) work with zero network.
- **Full offline parity, not a lighter version**: the entire active-employee roster (system-wide, unscoped — a guard must be able to check in visiting personnel from any department) is pulled into IndexedDB (Dexie) and a MiniSearch fuzzy index on every kiosk load. Manual search always queries this local index (works identically online or offline, since the whole roster is already client-side — a genuine simplification over legacy, which hits a server search endpoint online and only falls back to local search offline). Movements are queued locally (`client_request_id`-tagged) when offline or when a live submit fails, and flushed automatically on a 15s retry timer once back online.
- **No migration needed** — `movements.client_request_id` (UNIQUE) and the composite UNIQUE `(emp_id, mvtype, mvdate, mvtime)` already exist live on the shared DB from the old backend's own migrations. `Movement::$fillable` was entirely absent (added it) — nothing could create a movement before this.
- **Consolidated legacy's two write endpoints into one**: `check-manual`/`check-submit` both funnel into the same private `createMovement()` in legacy — ported as a single `POST /gate/submit` with an `automatic` boolean branching whether `mvdate`/`mvtime` are required (manual) or server-defaulted to `now()` (auto/scan). Also normalized legacy's inconsistent `empl_id` (a typo on the manual path only) to `emp_id` everywhere.
- **Alerts redesigned for i18n, not ported verbatim**: legacy's `EmployeeGateAlerts::build()` returns hardcoded Arabic sentences baked server-side. Ported the _classification_ logic only (`App\Application\Gate\EmployeeGateAlerts::classify()`) returning `{type, severity, expiry_date?}` — the frontend renders the message via `trans('gate.alerts.<type>', {date})`, matching this app's established i18n discipline everywhere else. Also dropped legacy's remark/expiry cross-suppression heuristic (it only existed to avoid two overlapping Arabic-phrased sentences — meaningless once messages are type-driven).
- **`crypto.randomUUID()` bug caught before it shipped**: it's only available in secure contexts (HTTPS/localhost) — this app is served over plain HTTP (confirmed: `https://` isn't even listening here), so every real movement submission would have silently thrown and never queued. Fixed via `resources/js/lib/gateOffline/uuid.ts`'s `generateClientRequestId()`, a manual RFC4122 v4 builder on `crypto.getRandomValues()` (no secure-context restriction), used everywhere a `client_request_id` is minted.
- **Real permission gap found and fixed on the live DB**: `config/access.php`'s `default_resource_access['Gate Guard']` was `[]` (now `['employees' => ['read']]`) — but that config is only a _fallback_ consulted when a role has zero real permission rows (`User::withAuthPayload()`), so editing it alone did nothing. The live `Gate Guard` role's real `role_has_permissions` rows were verified (via raw `DB::table()`, not cached Eloquent) to have only `route.gate`/`route.gate_plate_search` — **no `employees.read`**, meaning every JSON action endpoint (`directory`/`lookup`/`submit`/`sync`/plate-search, all gated on `employees.read`) was a hard 403 for the one role this entire feature exists for. Granted `employees.read` to the `Gate Guard` role via `Role::givePermissionTo()` (the same mechanism the Roles & Permissions admin page itself uses) + cleared the permission cache. Caught by a full Playwright run, not assumed from an earlier session's DB snapshot — that snapshot had gone stale by the time this page was actually built.
- **Verified end-to-end via Playwright** (throwaway Gate Guard test user + real employee, all cleaned up after): manual search → card preview → confirm → real `movements` row created; resubmitting the identical `client_request_id` directly against `/gate/submit` returned `duplicate: true` with no second row (idempotency proven through the real HTTP/FormRequest stack, not just the service layer in isolation); `/gate/plate-search` found the row by plate; full offline cycle — local roster search and card preview work with `context.setOffline(true)`, a submission queues (pending-count tag appears), reconnecting fires the 15s retry and the queue clears via `/gate/sync`. In one run the offline-queued check-in landed in the same clock-minute as an immediately preceding online one for the same employee and was correctly classified `duplicate` (not a bug — the composite unique index doing exactly its job of not double-counting a guard checking someone in twice across a connectivity blip).
- **Bug found and fixed while building `PlateMovements.vue`**: the results table never actually rendered a `platenumber` column despite being a _plate_ search — added it, plus fixed `mvdate` rendering the raw ISO timestamp instead of just the date.
- **Not fixed, pre-existing, unrelated**: `employeePhotoUrl()`'s placeholder path (`/uploads/nopic.jpg`) 404s — the file doesn't exist in gateNew's `public/uploads`; same shared helper used by Employees/Companies, not something this page introduced.
- **Chromeless layout, matching legacy exactly** — re-read `gate/frontend/src/pages/gate/GateKiosk.vue` + `router/index.js` on request: legacy wraps `/gate` and `/gate/plate-search` in a bare `BlankLayout` (`hideNav: true`), not its `AppShellLayout` (sidebar) — the kiosk page carries its own small embedded header (logout, base/context label, user greeting) instead. Ported the same split: new `resources/js/layouts/GateLayout.vue` (logout button, locale toggle, user greeting, `<Toast/>`/`<ConfirmDialog/>` — a page under this layout still needs those since they're normally only mounted by `AppLayout`) replaces `AppLayout` on both `GateKiosk.vue`/`PlateMovements.vue`.
